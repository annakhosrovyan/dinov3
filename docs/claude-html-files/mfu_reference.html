① vit_forward_flops() — mfu.py:20

Computes MACs for one forward pass of a ViT on one image at a given sequence length. This is the mathematical foundation — everything else calls this.

Per-layer MAC breakdown

attn_linear 4 × seq_len × D² # Q, K, V, O projections
attn_scores 2 × seq_len² × D # QKᵀ + AV (bidirectional, full square)
ffn 2 × seq_len × D × ffn_dim # MLP up + down
total_MACs num_layers × (attn_linear + attn_scores + ffn)

Concrete numbers — ViT-B/16, satellite config

Cropseq_lenMACs / fwd
Global 224×224 197 (14×14 + CLS) ~17.4 GMACs
Local 96×96 37 (6×6 + CLS) ~3.3 GMACs
17.4 GMACs for ViT-B/16 global crop matches the DINOv2 paper — used as a paper-anchor sanity check in test_mfu.py.
Why quadratic? The attn_scores term is seq_len². At 197 vs 37 tokens, global crop is ~28× more expensive on attention alone, but FFN dominates at these sizes so the ratio is ~5×.

Key assumptions baked in

Bidirectional attention
Full seq_len × seq_len matrix — no causal mask savings. ViTs always attend to all tokens.
ffn_ratio = 4.0
Standard MLP: ffn_dim = 4 × D = 3072. Not SwiGLU (which uses 2/3 × 4 × D). Controlled by cfg.student.ffn_ratio.
n_registers = 0
Satellite fork drops register tokens. seq_len = (crop // patch)² + 1 (patches + CLS only). Confirmed from ssl_default_config.yaml.

② compute_dino_flops_per_image() — mfu.py:52

Assembles the full student-teacher workload: student forward+backward, teacher forward, optional gram teacher forward, plus a head overhead factor.

Workload breakdown formula

student_fwd 2×global_fwd + 8×local_fwd
student_bwd 2 × student_fwd # chain rule: 2× forward
teacher_fwd 2×global_fwd # global crops only, no grad
gram_fwd 2×global_fwd if gram_enabled else 0
return (student_fwd + student_bwd + teacher_fwd + gram_fwd) × 1.05 # +5% head overhead

Concrete total — default config

ComponentGMACs
student_fwd (2 global + 8 local)61.2
student_bwd (2× fwd)122.4
teacher_fwd (2 global)34.8
gram_fwd (disabled)0
head overhead (+5%)+10.9
Total~229 GMACs
CLAUDE.md records ~226 GMACs; test suite expects 200–245 GMACs. Slight differences come from rounding.

Why student_bwd = 2 × student_fwd

Backprop runs chain rule through every layer. For each layer the backward pass performs two matmuls the same size as the forward matmul: (1) gradient w.r.t. weights dL/dW and (2) gradient w.r.t. input dL/dX. That's 2 forward-equivalent units of work per layer — hence backward ≈ 2× forward. The teacher uses torch.no_grad() so it has no backward pass and doesn't appear here. EMA update (_foreach_mul_/add_) is cheap enough that it's excluded from FLOP counting entirely.

③ compute_mfu() — mfu.py:111

Converts throughput (images/sec) + MACs/image → fraction of GPU peak.

Formula

Step 1 — MAC → hardware FLOP
actual_tflops = (images_per_sec × 2 × macs_per_image) / 1e12
Step 2 — Divide by peak
MFU = actual_tflops / (num_gpus × peak_tflops)
Logged as percentage
mfu_pct = MFU × 100

The 989 TFLOPS constant — why not 1979?

NVIDIA's H100 spec sheet lists 1979 TFLOPS BF16 — but that number assumes 2:4 structured sparsity, which roughly doubles theoretical throughput by skipping every other weight in a specially arranged sparse format.

Standard ViT training uses dense matmuls. The real dense BF16 peak is:
1979 ÷ 2 = 989 TFLOPS (dense)
Using 1979 as the denominator would make MFU look 2× lower than reality. Reference: Stas Bekman's ML Engineering book; NVIDIA H100 datasheet footnote.
There are two separate 2× multipliers in this pipeline — they serve completely different purposes. See the Gotchas section below.

⚡ Critical Gotchas — The Two 2× Multipliers

2× #1 — Backward pass (in compute_dino_flops_per_image)
student_bwd = 2 × student_fwd
What it models: The gradient computation through each layer requires two extra matmuls (dL/dW and dL/dX), each the same cost as the forward pass.
Unit stays: still MACs.
2× #2 — MAC → hardware FLOP (in compute_mfu)
actual_tflops = (ips × 2 × macs) / 1e12
What it models: 1 MAC = 1 multiply-add = 2 hardware FLOPs. Hardware vendors count the multiply and the add separately.
Unit changes: MACs → hardware FLOPs (matching what NVIDIA's TFLOPS rating counts).
These are independent of each other. Don't conflate them: one is about the training algorithm (backward), the other is about hardware accounting (MAC vs FLOP unit).
