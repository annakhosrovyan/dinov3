The Two Blockers — What They Are and How They Differ

Both bugs lived in the CUDA-graph infrastructure layer, not in the training math. Both had zero symptom in any prior job because cudagraphs: false was always the config. The fullgraph=True branch in ac_compile_parallelize.py had never executed before Phase 6.

BLOCKER 1 Buffer aliasing at graph tree level

Layer: CUDA graph replay infrastructure (cudagraph_trees.py)

Trigger: Multiple invocations of the same compiled function within one step, with different input shapes. Here: global crops (197 tokens) and local crops (37 tokens) — each compiled block is called twice per student + twice per teacher.

Mechanism: Inductor builds a tree of sub-graphs — one leaf per distinct input shape. Without mark_step_begin(), it doesn't know when a "step" ends, so it allows the output buffer from sub-graph A to be reclaimed for sub-graph B's input recording. When sub-graph A's output is accessed later in the backward, it has been overwritten.

Fix: one-line API call at step boundary. No model code changed.

Status: FIXED in ssl_meta_arch.py:387

BLOCKER 2 index_put_(accumulate=True) in backward

Layer: Inductor CUDA graph capture decision

Trigger: Stochastic-depth token subsampling in each transformer block. The block samples a random subset of tokens for attention and MLP, using x[indices] advanced indexing to gather the subset.

Mechanism: x[indices] in forward is a gather. PyTorch autograd translates the corresponding backward to a scatter-add — specifically index_put_(output, indices, grad, accumulate=True). Inductor explicitly refuses to capture this op into CUDA graphs (scatter operations with accumulate break the "no side effects" assumption of graph replay).

Fix: replace x[indices] with torch.index_select(x, 0, indices) — identical forward numerics, but backward is index_add, which Inductor captures cleanly.

Status: FIXED — confirmed in job 53681 (0 warnings, +44.8 % img/s)

Why blocker 2 appeared after blocker 1 was fixed Job 53655 crashed before a single iteration completed — Inductor threw at input-recording time for the buffer aliasing. The index_put_ decision happens later, at capture time during the first few iterations. Blocker 2 was always present; blocker 1 just killed the job first.

How Inductor's CUDA Graph Tree Works (and Why _forward_list Stresses It)

Understanding why both blockers appeared requires understanding how Inductor manages CUDA graphs for compiled modules that see multiple distinct input shapes.

Normal single-shape case

If a compiled function always receives the same input shape, Inductor records one CUDA graph and replays it every time. Output buffers are stable; no aliasing possible.

# same shape every call → one graph
block(global_tokens)  # shape (B, 197, 768)
block(global_tokens)  # same shape → replay same graph

Multi-shape case: _forward_list

DINOv3 passes both global (197 tokens) and local (37 tokens) crops through each block in one call via _forward_list. Inductor sees two shapes — it records two sub-graphs and must track which one to replay.

# two shapes → two sub-graphs per block
block([global_tokens,  # shape (B, 197, 768)
       local_tokens])  # shape (B*8, 37, 768)
# + teacher calls both too → 4+ invocations
mark_step_begin() as a fence The CUDA graph tree uses output buffer aliasing as an optimization — it reuses memory between sub-graph invocations to reduce total allocation. cudagraph_mark_step_begin() inserts a fence: "no buffers from before this call may be reused until the current step's graphs have completed." Without it, the tree reuses the global-crops output buffer for the local-crops graph input recording — destroying the global-crops activations that the backward still needs.
Why this never triggered before Phase 6 With cudagraphs=false, module.compile() uses Triton-compiled kernels but launches them through the normal CUDA stream — no graph recording, no replay, no aliasing possible. The multi-shape _forward_list path has always worked correctly in eager mode and in standard compile mode.

The index_select Fix — Why the Same Operation Behaves Differently in Autograd

Stochastic depth in each transformer block randomly drops a fraction of token vectors before running attention and MLP, then adds the residual back to the full sequence. The original code used Python's standard slice/index notation:

# Original: gather a random subset of token vectors
indices_1 = (torch.randperm(b, device=x.device))[:sample_subset_size]
x_subset_1 = x[indices_1]         # advanced indexing — gather tokens
residual_1 = self.attn(self.norm1(x_subset_1), rope=rope_subset)

# Then scatter the residual back using index_add
x_attn = torch.index_add(x, dim=0, source=self.ls1(residual_1), index=indices_1)

x[indices] — what autograd actually does

In forward: gather rows from x at positions indices. Straightforward.

In backward: the gradient w.r.t. x must scatter grad_output back to the original positions. PyTorch implements this as:

x.index_put_(
    (indices,), grad_output,
    accumulate=True   ← this flag
)

The accumulate=True flag is necessary because the same index can appear multiple times (e.g. if randperm happened to put the same token index twice — which it can't, but Inductor doesn't know that). Inductor refuses to record ops with accumulate=True into a CUDA graph because scatter-add in general has data-dependent memory access patterns that break the strict replay semantics.

torch.index_select — the capturable alternative

In forward: identical output to x[indices] — gathers the same rows.

In backward: the gradient w.r.t. x is computed as index_add:

grad_x = torch.zeros_like(x)
grad_x.index_add_(
    0, indices, grad_output
    ← no accumulate flag needed
)

index_add (without accumulate) is capturable because Inductor can statically determine the memory layout: each output position receives exactly one contribution, determined by the fixed index tensor. Inductor accepts this and includes it in the CUDA graph.

Numerical equivalence When indices has no repeated entries (which randperm guarantees), x[indices] and torch.index_select(x, 0, indices) produce identical forward outputs and identical gradients. The change is purely at the autograd-op-selection level — no precision change, no loss change.
Why stochastic depth uses a random subset in the first place Stochastic depth during training randomly drops a fraction of token vectors (controlled by sample_drop_ratio) before the attention and MLP sub-layers, then rescales the residual to compensate. This is a regularization technique. For ViT-B the drop ratio defaults to a small value (e.g. 0.1–0.2), so typically 80–90 % of tokens are processed — the full 197-token sequence is never fully dropped. The important point is that even though the subset size is the same every iteration (it is deterministic: max(int(b * (1 - ratio)), 1)), the indices change (it's a fresh randperm each step). With dynamic=False, Inductor captures a graph for a fixed subset size — but the index values are treated as variable graph inputs, not baked in. The graph replay mechanism is shape-static but value-dynamic, which is why this can work once the right autograd op is used.

Background: How torch.compile Is Wired in This Repo

This section describes the compile infrastructure as it existed before Phase 6 and has not changed substantially. It explains why the fullgraph/CUDA-graph branch was present but never executed.

The Wrapper Stack

The compile behavior is hidden behind a project wrapper. train.compile=true does not directly call torch.compile — it goes through a four-step wrapper that selects which compile variant to use based on config flags.

1. Configssl_default_config.yaml
sets compile flags
2. Gateif cfg.train.compile
turns wrapping on
3. Mode Map_get_compile_mode()
null/default → None
4. Branchwrap_compile_block()
chooses fullgraph, mode, or default
# dinov3/fsdp/ac_compile_parallelize.py:65-76
if use_cuda_graphs and is_backbone_block:
    # Phase 6.A target — fullgraph + CUDA graphs
    module.compile(fullgraph=True, dynamic=False, options={"triton.cudagraphs": True})
elif compile_mode is not None:
    module.compile(mode=compile_mode)
else:
    module.compile()  # ← Phase 5 default: dynamic=True, no fullgraph, no CUDA graphs
The Phase 5 default path Every Phase 5 job used compile_mode: null + cudagraphs: false, which means the else: module.compile() branch at every compiled block. This is PyTorch's default-everything mode: Dynamo traces with dynamic shapes allowed, Inductor selects kernels opportunistically, graph breaks tolerated silently, no CUDA-graph capture attempted. It is the most permissive and least optimized of the three branches.

The iBOT Dynamic Shape Problem — Why It Is Separate from the Backbone

The two blockers above are backbone issues. There is a third, independent blocker that affects the heads and loss path — the iBOT stochastic masked-token count. It is separate from the index_put_ fix and requires its own Phase 6.B work.

Backbone: static

The ViT backbone sees fixed-shape inputs every iteration: global crops are always (B, 197, 768), local crops are always (B×8, 37, 768). With dynamic=False, these shapes are baked into the compiled sub-graphs and replayed efficiently. The backbone is already static-shape capable.

This is why Phase 6.A tests backbone CUDA graphs first, independently from Phase 6.B.

iBOT head path: dynamic

The iBOT loss operates on a variable number of masked patches K per batch. K comes from:

# collate.py:63
mask_indices_list = collated_masks.flatten()
    .nonzero().flatten()  # shape (K,) — varies each iter

K feeds masked_patches_pre_head shape (K,D), masks_weight shape (K,), and loss[:n_masked_patches] — all dynamic. Enabling fullgraph/CUDA-graphs on heads without fixing this causes Inductor to recompile every iteration (Phase 4 confirmed this costs minutes, not milliseconds).

Phase 6.B: Option B (padding to K_max) The plan is to pad mask_indices_list and masks_weight to a fixed upper bound K_max = ceil(mask_ratio_max × B × N_patches), with zero weights on pad rows so they don't contribute to the loss. This preserves the SSL recipe exactly while making all downstream shapes static. Gated on seeing a positive result from 6.A.3.

Compile Term Dictionary

These concepts are distinct layers — collapsing them into "compile" creates confusion when debugging which layer a problem lives in.

TermWhat it meansIn this codebase
train.compile=true Repo config flag — turns on module wrapping. Calls module.compile() on each transformer block, ConvNeXt stage, and head. Does not imply fullgraph or CUDA graphs.
torch.compile / module.compile() PyTorch's Dynamo + Inductor pipeline. Traces Python code into an IR, then generates optimized kernels. Default mode: dynamic=True, tolerates graph breaks. Used in all Phase 5 runs.
fullgraph=True Require the traced region to produce a single graph with no breaks. Fail loudly otherwise. Active in Phase 6.A via the is_backbone_block branch. Useful as a diagnostic: graph-break errors point to the exact unsupported op.
dynamic=False Specialize compiled code to the first observed input shapes. Recompile only if a shape outside the guard range appears. Used in the backbone CUDA-graph branch. The backbone is static-shape, so no recompile is expected.
CUDA graphs (triton.cudagraphs=True) Record the entire sequence of GPU kernel launches once, then replay the recording each step — eliminating the per-kernel CPU launch overhead. Enabled by the Phase 6.A backbone branch. Requires all ops in the captured region to be graph-capturable (no index_put_ accumulate=True, etc.).
cudagraph_mark_step_begin() Tell Inductor's graph tree that a new logical step is beginning. Prevents output buffer aliasing across sub-graph invocations within one step. Added at top of forward_backward(). Required when any compiled function is called multiple times per step with different input shapes (which _forward_list does).
Graph break A point where Dynamo stops tracing and returns to eager Python. Subsequent code runs outside the compiled graph. Phase 6 fullgraph mode turns silent breaks into hard errors — useful for finding hidden breaks. The known break source is checkpoint_wrapper in AC runs.
index_put_(accumulate=True) A scatter-add op in autograd. Produced by x[indices] gather in forward. Inductor refuses to capture this into CUDA graphs. Fix: use torch.index_select instead; its backward is index_add, which is capturable.
