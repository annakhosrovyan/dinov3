Torch Compile in DINOv3 - Phase 5 to Phase 6

A code-anchored explainer for what train.compile=true actually does, what Phase 5 tested, and what Phase 6 changes in response to Armen's fullgraph/static-shape recommendation.

Updated: 2026-05-22

Bottom Line

We have been using PyTorch compile. In this repo, train.compile=true routes DINOv3 modules through nn.Module.compile(), which is PyTorch's module wrapper for torch.compile.

But Phase 5 did not validate Armen's stronger proposal. The default path is compile_mode: null plus cudagraphs: false, so most runs used plain module.compile(), not fullgraph=True, dynamic=False, or CUDA graph capture.

Phase 6 is the direct answer to Armen: use DDP as the main path, test backbone-only CUDA graphs first, then make the iBOT masked-token path static enough for end-to-end fullgraph/CUDA graph testing.

Phase 6 At A Glance

Phase 5 answered many FSDP2 questions, but it left the most important compile question only partially tested. Phase 6 reframes the project around a simpler distributed setup and a stricter compiler target.

Abstraction Dictionary

These words are easy to collapse into one vague idea called "compile." They are different layers.

Term Plain meaning In this repo
train.compile=true Turn on the repo's compile wrapper. Eventually calls module.compile() on transformer blocks, ConvNeXt stages, heads, and teacher/student modules.
torch.compile / module.compile() Ask PyTorch Dynamo/Inductor to capture Python/PyTorch code into compiled graphs and generate faster kernels or launch patterns. Used by default, but without strict fullgraph enforcement unless train.cudagraphs=true hits the special branch.
fullgraph=True Require the whole region to compile as one graph. If something cannot be captured, fail instead of quietly breaking the graph. Useful as both an optimization attempt and a diagnostic. Failure tells us exactly which operation or dynamic shape blocks capture.
dynamic=False Tell compile to specialize to fixed shapes instead of accepting shape variation. Potentially faster, but only if the tensors passed through the compiled region really have stable shapes.
CUDA graphs Record a repeated sequence of GPU kernel launches and replay it with much lower CPU launch overhead. Wired for backbone blocks through options={"triton.cudagraphs": True}, but disabled by default.
Graph break A point where PyTorch cannot keep tracing and must return to Python eager execution. Bad for launch overhead and fusion. Phase 6.1 should identify whether we are paying this cost today.
Recompile PyTorch builds a new compiled graph because inputs or guards changed. Expected if masked-token counts keep changing. Too many recompiles can erase compile benefits.
Static shape The tensor dimensions seen by compiled code stay the same across iterations. Global/local crop image shapes can be fixed while iBOT masked-token tensors remain dynamic.

The compile behavior is hidden behind a project wrapper. That is why train.compile=true can look different from a direct torch.compile(...) call.

Default Compile Mode vs CUDA Graphs

Default compile mode means compile_mode: null, which the helper maps to plain module.compile(). It lets PyTorch/Dynamo/Inductor decide how much of the function to capture and where to tolerate graph breaks.

CUDA graph/fullgraph mode in this repo means the explicit branch:

module.compile(fullgraph=True, dynamic=False, options={"triton.cudagraphs": True})

This is stricter. It asks PyTorch to capture the whole block and use static assumptions. If Python code, unsupported ops, or dynamic tensor shapes violate those assumptions, it should fail loudly or recompile rather than silently acting like the default path.

Why Armen asked about fullgraph=True The point is not only speed. It is also a debugging tool. If fullgraph fails, the error is valuable: it tells us the exact operation, control flow, mutation, or shape dependency that prevents graph capture.

Why Fixed Images Are Not Enough

Armen's question, "why are the shapes not static if you resize into fixed shape?", is the right question. The answer is that DINOv3 has more shapes than image height and width.

Static-looking part

The global and local crops can have fixed image sizes. For ViT, those translate into fixed token counts such as global crop tokens and local crop tokens.

This is why Phase 6.2 tests backbone-only CUDA graphs first: the backbone may already be static enough.

Dynamic part

iBOT chooses a stochastic mask. The tensor mask_indices_list is built with .nonzero(), so its length depends on how many patches were masked in that batch.

That dynamic length then affects tensors such as student_patch_tokens_masked and teacher_patch_tokens_masked.

Code references: dinov3/data/collate.py:63,71,74; dinov3/train/ssl_meta_arch.py:399,585,676.

Practical translation Fixed resize can make the image tensor static, but the masked-token tensor can still be dynamic. Phase 6.3 is about making that masked-token side static, most likely by padding to a fixed maximum and masking out the padding in the loss.

The Dynamic Shape Problem

The documented blocker is not image resize alone. The specific issue is the stochastic iBOT masked-token count, which changes tensor shapes at training time.

Prior compile-mode screening says a compiled kernel for one masked-token shape, such as shape 7503, would fail on the next iteration's different shape. The same section concludes max-autotune-no-cudagraphs was fundamentally incompatible with the current model setup.

Source: docs/perf_experiment_log.md:646-650; summary reminder in CLAUDE.md:286.

Open Questions for Phase 6

Question Why it matters How Phase 6 answers it
Is current module.compile() repeatedly recompiling? If yes, current compile is spending time adapting to changing shapes instead of delivering stable optimized execution. Phase 6.1 logs recompiles, graph breaks, and dynamic guards.
Can backbone blocks use CUDA graphs before fixing iBOT? If yes, we can capture a major compute region without solving the hardest dynamic-shape problem first. Phase 6.2 flips train.cudagraphs=true for the existing backbone-only branch.
How expensive is padding iBOT masked tokens? Padding buys static shapes, but it may add wasted compute. The win depends on whether graph/cuda launch savings exceed padding overhead. Phase 6.3 measures padded vs real masked-token counts and performance before fullgraph is layered on.
Does DDP remove enough complexity compared with FSDP2? DDP keeps full parameters resident and has simpler communication and wrapping. That makes compiler behavior easier to reason about. Phase 6 treats DDP as the operating path for this 85M-100M parameter model.
Can fullgraph fail usefully? A failure is still progress if it identifies the exact code path preventing capture. Phase 6.4 should preserve full errors and map them back to source lines.

Trade-Offs

Choice Upside Risk / cost Current stance
DDP instead of FSDP2 Much simpler wrapping; easier compiler and CUDA graph path; no FSDP reshard state machine. Higher parameter memory than sharded FSDP, but ViT-B scale should fit comfortably on H100. Phase 6 default.
Backbone-only CUDA graphs Low-code-change test of Armen's idea; avoids iBOT dynamic heads initially. May not cover enough of the step to move MFU by itself. Phase 6.2.
Padding iBOT tensors Makes downstream shapes static and potentially unlocks fullgraph/CUDA graph replay. Extra padded tokens can waste head/loss compute and must preserve loss normalization. Phase 6.3 pilot before end-to-end fullgraph.
fullgraph=True Strong diagnostic; can eliminate silent graph breaks and force a cleaner optimized path. May fail hard on unsupported Python/control-flow/mutation patterns. Use deliberately, preserve errors.
Relying on archived 100-iter DDP numbers Suggests DDP may have a high ceiling. Short-run numbers can be compile-warmup or measurement-window artifacts. Historical context only; do not promote without 1000-iter replication.

How To Read Phase 6 Results

A good Phase 6 result is not just "it ran faster once." It needs to distinguish compiler warmup, steady state, shape recompiles, and communication overhead.

  • Use iter 400-999 for the main steady-state comparison, matching the current Phase 5 convention.
  • Track median and CV, not only mean. High CV means the average may be dominated by bursty stalls.
  • Preserve compile logs. Recompile and graph-break counts explain why a run is fast or slow.
  • Keep padding telemetry. If static iBOT padding is added, log real masked-token count, padded count, and padding ratio.
  • Separate backbone and iBOT effects. Phase 6.2 can win without proving full-step static shape; Phase 6.4 is the full test.

Precise Wording to Use

We used DINOv3's train.compile=true, which compiles transformer blocks and other modules through nn.Module.compile(). In Phase 5, that generally meant PyTorch's default compile path with compile_mode: null and cudagraphs: false. Phase 6 is the test of the stronger proposal: DDP plus backbone CUDA graphs, then static iBOT shapes, then end-to-end fullgraph=True / CUDA-graph-style compilation.
