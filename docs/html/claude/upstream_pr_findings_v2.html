Upstream PR Findings

PR #324 clarifies the FSDP2 resharding knob. PR #340 makes gc.disable() a long-run worker-RSS risk.

PR #324: Resharding

Upstream public DINOv3 had fully_shard(..., reshard_after_forward=True) hardcoded, so compute_precision.sharding_strategy did not control FSDP2 behavior.

Our fork appears to pass train.fsdp_reshard_after_forward into trained-model fully_shard(...) calls, so Phase 5 reshF runs are probably valid.

Source: facebookresearch/dinov3#324

PR #340: Python GC

Older docs treated gc.disable() plus periodic gc.collect() as a straggler mitigation. PR #340 shows disabled cycle GC can let torchvision.transforms.v2 reference cycles accumulate in DataLoader workers.

Keep periodic manual collection if useful, but do not treat disabled automatic GC as safe for long training.

Source: facebookresearch/dinov3#340

Corrected Read Of Our Docs

reshard_after_forward=false is basically DDP.It is DDP-like, but still uses FSDP2 wrapping, prefetch scheduling, and bookkeeping.

GC Leak Mechanism

1torchvision.transforms.v2 calls pytree flattening.
2Short-lived Python reference cycles are created.
3With automatic cycle GC disabled, cycles are not collected.
4Tensor storage refs and shared-memory FDs accumulate.
5DataLoader worker anonymous RSS grows over long runs.

Follow-Ups

  • Deprecate or remove compute_precision.sharding_strategy from maintained docs/configs.
  • Add startup logging for distributed strategy, fsdp_reshard_after_forward, and AC mode.
  • Add a small FSDP state audit instead of inferring reshF from throughput.
  • Remove or gate gc.disable(); keep periodic manual gc.collect() if useful.
  • Track DataLoader worker RSS in long soaks when memory growth is suspected.
