Phase 7 — The flat-MFU residual

Why DDP+cudagraphs MFU pins flat at ~20–21% across bs=128/160/192 — and what to do about it.

Summary of docs/phase7_perf_plan.md · current as of 2026-06-23 · objective unchanged since 2026-06-11

The one-paragraph story

Phase 6 left a residual: increasing batch size (128 → 160 → 192) raised wall-clock throughput modestly but MFU stayed flat — the GPUs were not getting more efficient. Phase 7 opened believing the residual was compute (head FLOPs, the "dynamic iBOT mask shape" problem → pad → unlock max-autotune). The first real nsys trace (job 75082) disproved that: the dominant residual is inter-rank communication / synchronization, not compute. The compute analysis is preserved as the record of why we now know it's comms, but all live work targets collectives and per-iteration sync barriers.

Why it's still "Phase 7," not "Phase 8" A phase tracks an objective ("why is MFU flat, how do we fix it"), not a mechanism. Only the suspected cause flipped (compute → comms); the objective is the same, so the sub-indexing (7.0…7.7) is kept and artifacts citing 7.1/7.2 stay valid.

Step wall here (~769 ms, ~1,330 img/s) is slower than the bare champion screen (~428 ms, ~2,394 img/s) because of nsys attach overhead. Trust the shares, not absolute ms.

The crucial caveat — why the numbers mislead if read naively NVTX ranges are CPU push/pop times; NCCL collectives are enqueued async on a separate stream. So the 32.6% in allreduce_metrics is largely "the bill coming due" — the GPU finally waiting for deferred async collectives + rank skew at the first hard sync after backward — not the intrinsic cost of its own scalar-sized collective. NVTX shows where Python waited, not where the responsible GPU work was created.

The two communication sinks

  • allreduce_metrics — an unconditional, blocking gather+reduce every iteration for NaN-checking and logging (train.py:652-667), even though metrics are only logged every ~10 iters. Payload is a few scalars, so it's almost entirely synchronization wait.
  • NCCL is ~93% exposed, split into two kernels: AllReduce…bf16 (264 ms/iter) = the DDP gradient all-reduce; and AllReduce…f32 (494 ms/iter, largest single kernel) = a mixture of loss-side fp32 collectives (DINO/iBOT Sinkhorn + center + the metrics reduce), not gradients. Protocol fell back to RING_LL because we unset NCCL_NVLS_ENABLE.

Leading hypothesis (unproven): CUDA-graph backward materializes all grads at replay-end, so the bf16 grad all-reduce can't hide behind backward compute → 93% exposed. The 7.5 control trace is the clean test of this.

Running now — 7.2 stream-connections sweep

Hypothesis (Codex #1 by info-per-GPU-hour): CUDA_DEVICE_MAX_CONNECTIONS=1 is inherited from the FSDP2/Megatron-era recipe (where =1 forces TP collective ordering). It collapses CUDA streams onto one hardware work queue, which can serialize the NCCL stream behind compute — exactly the 93%-exposed failure mode. For pure DDP (no tensor parallelism) it's likely unnecessary and possibly harmful. NVIDIA's default is 8.
