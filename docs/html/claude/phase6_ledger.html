Phase 6 Journey — How We Got From 7.94% to 13.70% MFU three diagnostic failures + three engineering wins
Baseline established job 48312 · 2026-05-21
DDP bs=96, compile=true, cudagraphs=false (i.e., the legacy code path: module.compile() with dynamic=True). 1,387 img/s, 7.94% MFU, 545 ms/step. This was the floor we were measuring lifts against.
First cudagraphs attempt crashed job 53655 · 2026-05-22
First time anyone in this codebase had set train.cudagraphs=true — code path had been wired for months but never exercised. RuntimeError: accessing tensor output of CUDAGraphs that has been overwritten by a subsequent run at block.py:194. Root cause: Inductor's cudagraph tree aliased output buffers across the teacher fwd, student fwd, and the two crop-size sub-graphs within a single forward_backward() call. Fix: torch.compiler.cudagraph_mark_step_begin() at the top of forward_backward in ssl_meta_arch.py (no-op when cudagraphs off; signals new step to the cudagraph tree).
Second attempt regressed 10% job 53672 · 2026-05-22
1,244 img/s, 7.12% MFU — slower than baseline despite cudagraphs being on. Stderr showed 8 lines of "skipping cudagraphs due to index put with accumulate" originating from x[indices] advanced indexing inside block.py:_forward_list. The backward of advanced indexing produces index_put_(accumulate=True), which Inductor refuses to capture into cudagraphs. Fallback to eager + cudagraph tree overhead = net regression.
Fixed index_put with index_select block.py · 5 sites · 2026-05-22
Replaced x[indices] with torch.index_select(x, 0, indices) at 5 sites in _maybe_index_rope, _forward, and _forward_list. Mathematically identical for unique torch.randperm indices (which they are — sample drop). Critical difference: backward of index_select is index_add (graph-capturable). All sites inside the if self.training and self.sample_drop_ratio > 0.0 branch — only stochastic-depth path affected.
First win — cudagraphs at bs=96 job 53681 · 2026-05-22
2,009 img/s, 11.50% MFU, 379 ms/step. +44.8% throughput vs baseline. The fullgraph + triton.cudagraphs path finally compiled cleanly across the entire backbone. Validates Armen Aghajanyan's hypothesis: ViT-B step time was Python/launch-overhead-bound, not compute-bound; cudagraphs eliminated the launch tax.
Batch scaling win — bs=128 ★ CHAMPION job 53708 · 2026-05-22
2,394 img/s, 13.70% MFU, 34.1 GB peak. +19.2% over 53681; +72.6% over baseline. Step time barely grew (379 → ~390 ms) because the bottleneck had shifted from per-step launch overhead to compute. Memory scaled almost perfectly linear from 25.8 → 34.1 GB. Cumulative gain: +5.76 pp MFU.
bs=192 OOM job 53739 · 2026-05-23
Linear prediction said ~51 GB peak; actual exceeded 80 GB. Cudagraph workspaces scale non-linearly past bs=128. Inductor's cudagraph tree holds per-shape sub-graph workspaces; growing batch grows them faster than activation memory. This invalidated the AC-isn't-needed narrative — AC is now the only path to bs≥192.
AC sweep (×4) characterizes the tradeoff jobs 53740, 53742, 53999, 54000 · 2026-05-23/24
Mapped {bs=96, bs=128} × {AC=sel, AC=full} at cudagraphs=true. Two surprises:
(1) AC=full dominates AC=sel — same throughput, ~35% less memory. The selective save list covers fast-to-recompute ops (mm, SDPA) but not bulky activations (norms, residuals); sel doesn't save much memory.
(2) AC throughput cost is batch-independent at ~31%. Fullgraph + triton.cudagraphs survived both AC modes (all 12 blocks still on the cudagraphs branch per [COMPILE] logs).
Config bug found mid-sweep: checkpointing_full=true alone does not enable AC (needs checkpointing=true too). Original 53741/53743 invalidated; re-runs 53999/54000 used correct config.
bs=192 attempt — host-RAM OOM job 56131 · 2026-05-25
OOM, but root cause was wrong in the earlier bs=192 diagnosis. Not VRAM / cudagraph workspace overflow — host RAM. The DataLoader configuration (8 ranks × 20 workers × prefetch=8) keeps a large pinned-memory working set on the host. At bs=192 that pool exhausts system RAM before any GPU memory limit is hit. Critical implication: AC is irrelevant to this constraint. Activation checkpointing frees device VRAM, not host pinned memory. The path to bs≥192 requires a loader rework (fewer workers, lower prefetch, or a streaming loader), not just enabling AC. Phase 6.A batch-scaling ceiling is therefore bs=128 on this configuration.

Key surprise — AC=full dominates AC=sel here. Same throughput, ~35% less memory. The codebase's selective save list (mm, SDPA, scaled_mm, reduce_scatter) saves the fast-to-recompute ops but not the bulky-to-store activations (norms, layer-scale, residuals, dropout state). Full saves much more memory for nearly the same recompute cost. Drop AC=sel from future runs.

Why the index_select fix mattered
Oldx_subset = x[indices] — advanced indexing
Newx_subset = torch.index_select(x, 0, indices)
MathIdentical for torch.randperm indices (guaranteed unique)
Old backwardindex_put_(accumulate=True) — Inductor refuses to capture
New backwardindex_add — Inductor captures cleanly
Sites5 in block.py (rope index, _forward, _forward_list)
RiskNone — drop-in equivalent for the only callsites (sample drop with unique indices)
Why mark_step_begin mattered
SymptomRuntimeError accessing tensor output of CUDAGraphs that has been overwritten by a subsequent run
Root causeOne forward_backward() call enters compiled backbone 4+ times: teacher fwd, student fwd, global crops, local crops. Without a step marker, Inductor's cudagraph tree aliases output buffers across them.
FixCall torch.compiler.cudagraph_mark_step_begin() at top of forward_backward(). Tells the cudagraph tree a new step is starting → don't alias buffers from prior step into this step.
CostNo-op when cudagraphs are off. Single function call when on.
Referencetorch/_inductor/cudagraph_trees.py — see cudagraph_mark_step_begin + buffer reuse logic
Open Decision Questions
Q1 — bs=256+AC=full probe ✗ SUPERSEDED
Originally planned as the next batch-scaling probe. Closed by job 56131: bs=192 already OOM'd on host RAM from the DataLoader pinned pool (8 ranks × 20 workers × prefetch=8). AC saves device VRAM, not host pinned memory — AC=full cannot unlock bs≥192. The batch ceiling is bs=128 until the loader is reworked (fewer workers, lower prefetch, or streaming loader). bs=256 is not a near-term probe.
Q2 — Move to Phase 6.B ★ RECOMMENDED
Phase 6.B = extend fullgraph=True to DINO/iBOT heads + static-shape iBOT (eliminate mask-shape recompiles). Heads currently on module.compile() default (dynamic=True). Late-iter MFU variance in 53708 (instant 12.9–17.0%) is consistent with heads on a dynamic-shape compile path being the next bottleneck. Larger code lift than batch tuning, but the only remaining lever on this configuration that doesn't require structural changes (loader rework, multi-node, larger model). This is the next Phase 6 leg.
Q3 — Is 30% MFU achievable?
On ViT-B + 1× DGX H100 + DDP: probably no. ViT-B (86M params, seq_len 197/37) is small relative to H100; Tensor Core tile sizes don't fully populate. Reference ViT-B BF16 H100 numbers cluster at 15–22% MFU. The realistic ceiling for this stack is likely ~18–22% MFU. 30% would need ViT-L+, longer sequences, or both. Phase 6.B may add a few pp but won't close the full gap.
Q4 — Loss numerics regression check pending
53708's loss values match 48312 baseline qualitatively (dino ~9.87, ibot ~4.77). Have NOT run a strict A/B comparing first 100 iter loss curves between cudagraphs=true and cudagraphs=false with fixed seed. Should land before production switch.
