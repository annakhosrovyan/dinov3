Upstream DINOv3 PRs changed how we should read two Phase 5 assumptions.

PR #324 clarifies the real FSDP2 resharding knob. PR #340 changes gc.disable() from a presumed straggler mitigation into a long-run DataLoader worker RSS risk.

Resharding Verdict

Our fork appears to already have the important behavior from upstream PR #324: train.fsdp_reshard_after_forward is read and passed into trained-model fully_shard(...) calls.

Therefore the Phase 5 reshF jobs are probably real no-release FSDP2 runs, not accidental reshT reruns.

Source: facebookresearch/dinov3#324

GC Verdict

Older docs framed gc.disable() plus periodic gc.collect() as a mitigation. Upstream PR #340 shows that disabling automatic cycle GC can make torchvision.transforms.v2 reference cycles accumulate in DataLoader workers.

Keep periodic manual collection if useful; do not treat disabled automatic GC as a safe long-run default.

Source: facebookresearch/dinov3#340

What PR #324 Says

Upstream public DINOv3 had a config field named compute_precision.sharding_strategy, but that field did not control FSDP2 wrapping. The relevant fully_shard(...) calls were hardcoded with reshard_after_forward=True.

The upstream fix adds train.fsdp_reshard_after_forward, removes legacy sharding-strategy config entries, wires the new knob through SSL training FSDP wrapping, and keeps inference-only modules always resharded for predictable memory.

How This Changes Our Interpretation

Old Wording Corrected Wording
SHARD_GRAD_OP explains Phase 5 FSDP2 behavior. train.fsdp_reshard_after_forward is the actual Phase 5 behavior knob.
reshard_after_forward=false is basically DDP. It is DDP-like, but still uses FSDP2 wrapping, scheduling, and bookkeeping.
gc.disable() partially mitigates GC stragglers. It may reduce short-run GC timing noise, but it can cause long-run worker RSS growth.

GC Mechanism From PR #340

1torchvision.transforms.v2 calls pytree flattening.
2Short-lived Python reference cycles are created.
3With automatic cycle GC disabled, cycles are not collected.
4Tensor storage refs and shared-memory FDs accumulate in workers.
5Worker anonymous RSS grows over long training runs.

PR #340 reports roughly ~3.4 MB/iter worker RSS growth with gc.disable() and roughly ~0.01 MB/iter with cycle GC enabled in its controlled benchmark.

Practical Follow-Ups

  • Deprecate or remove compute_precision.sharding_strategy from our maintained docs and configs.
  • Add startup logging for train.distributed_strategy, train.fsdp_reshard_after_forward, and AC mode.
  • Add a small FSDP state audit so reshF behavior is verified directly, not inferred from throughput.
  • Remove gc.disable() or gate it behind an explicit experimental flag.
  • Keep periodic manual gc.collect() if we still want predictable rank-synchronized pauses.
  • For long soaks, track DataLoader worker RSS if memory growth is suspected.
