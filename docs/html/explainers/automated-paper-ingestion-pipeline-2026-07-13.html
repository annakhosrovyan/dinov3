Automated paper ingestion pipeline

Start with a thin local scheduled digest. Reuse official metadata APIs, keep Zotero as the durable paper library, and use ResearchRabbit only after a paper passes triage. Run a four-week pilot before adding learned local ranking or a larger web application.

Decision and operating model

Recommendation: pilot Proposal B, the thin scheduled digest. Local code fetches, normalizes, deduplicates, filters, ranks, and renders. It does not crawl sites, download PDFs, create a vector database, or replace ResearchRabbit.

What the earlier report contributes

  • arXiv is the regular source.
  • Conference proceedings are event-driven sources.
  • ResearchRabbit expands the citation graph after triage.
  • Project notes hold conclusions that matter for DINOv3 work.

What the deep-research report contributes

It adds a useful venue taxonomy and a concrete weekly reading routine.

Its calendar does not become application logic. Venue dates remain replaceable configuration because at least two calendar claims conflict with current official venue pages.

The plan adds the pieces neither report specifies fully: automated deduplication, feedback ownership, source-failure behavior, and false-negative checks.

Three proposals

FallbackLowest upkeep

A. Zotero-first feed hub

arXiv feeds enter a Zotero inbox. Manual tags and saved searches produce a kept collection, which is imported into ResearchRabbit weekly.

  1. Subscribe to narrow feeds.
  2. Use paper-inbox, paper-keep, paper-defer, and paper-reject.
  3. Save selections to GPU Performance.
  4. Create project notes only after deep reads.

Setup: one or two hours. Ranking: feed order and saved searches.

Constraint: the digest cap is manual and will not reliably yield two or three strong papers.

Recommended pilotMulti-source

B. Thin scheduled digest

A small local process combines arXiv, Hugging Face, and Semantic Scholar metadata, then applies canonical identity, hard rules, and a transparent score.

  • Produces dated Markdown and self-contained HTML.
  • Returns zero to three papers rather than filling a quota.
  • Stores cache state in SQLite, not durable decisions.
  • Writes decisions to Zotero tags and collections.

Setup: medium. Maintenance: low to medium.

Fit: enough automation to test time savings without operating a persistent application.

DeferLearned ranking

C. Self-hosted arxiv-sanity-lite

Reuse the arXiv poller, abstract TF-IDF features, per-tag SVM ranking, tagging UI, and recommendation email process from arxiv-sanity-lite.

  • ArXiv-centric unless extended.
  • Still needs Zotero export and ResearchRabbit handoff.
  • Still needs project-note conventions.

Setup: half a day to several days. Maintenance: highest.

Use only if: static ranking proves inadequate and a persistent browser UI is worth operating.

Recommended architecture flow

Proposal B separates source adapters, deterministic selection, human decisions, and downstream discovery. Zotero remains the decision authority throughout.

Source policy and identity

Source adapters

  1. arXiv: primary source. Query cs.DC, cs.PF, and filtered cs.LG. Add conditional cs.AR, cs.PL, and cs.CV terms for training systems or performance.
  2. Hugging Face: secondary popularity and code-community signal. Probe the installed huggingface_hub version, use list_daily_papers when available, and fall back to list_papers.
  3. Semantic Scholar: recommendations from a small positive and negative seed set. Resolve arXiv IDs or DOIs, cache good mappings, and skip uncertain title-only matches.
  4. Proceedings: event-driven adapter or manual import. Venue URLs and active dates belong in configuration.

The arXiv adapter caches responses, uses small result pages, makes at most one equivalent query per day, and respects the documented delay for repeated calls.

Canonical identity

  • canonical_arxiv_id without the version suffix
  • arxiv_version, published_at, updated_at, and first_seen_at
  • DOI when present
  • Semantic Scholar ID when confidently resolved
  • Normalized title hash only as a last-resort key
  • Source list and source-specific timestamps
Update rule: a new arXiv version does not re-enter the digest unless the title or abstract changes materially and the previous decision was defer. Formatting-only revisions stay suppressed.

Filtering, scoring, and digest contract

Stage 1

Hard rules

  • Accept configured categories and date window.
  • Require one positive family: distributed training, communication, compiler/runtime, input pipeline, memory, kernels, profiling, measurement, or training-system architecture.
  • Exclude application-only work with no systems or performance contribution.
  • Exclude already decided papers and exact duplicates.
Stage 2

Transparent score

score = topic_match
      + source_agreement
      + semantic_scholar_recommendation
      + hugging_face_signal
      + recency
      - negative_topic_penalty
      - near_duplicate_penalty
Version 1 scoring limits: do not infer code or artifact availability from abstract prose. Score it only when an adapter supplies structured metadata. An optional LLM reranker sees only the top 10 to 20 abstracts, returns a short reason tied to configured interests, and may fail without blocking the digest.

Digest contract

Selection: produce zero to three papers. Never fill the quota with low-scoring items.

Friday: roll up kept and deferred papers instead of creating another independent candidate batch.

  • Title, authors, date, and canonical links
  • Source provenance
  • Abstract compressed to at most three sentences
  • Why it may matter for DINOv3 performance work
  • One likely limitation or reason to skip
  • keep, defer, and reject instructions

Four-week pilot

Week 0: configure

  • Define queries, positive topic families, and negative terms.
  • Select three to five positive seeds and three to five clear negatives.
  • Create Zotero tags and GPU Performance.
  • Choose output directory and timer schedule.

Week 1: minimum loop

  • Implement arXiv fetch and canonical identity.
  • Add dedupe, hard filters, static score, and SQLite cache.
  • Render Markdown and HTML.
  • Record authoritative decisions in Zotero.

Week 2: secondary signals

  • Add Hugging Face dependency probing.
  • Add Semantic Scholar ID resolution and recommendations.
  • Add independent retries, source freshness, and provenance.

Weeks 3 and 4: tune

  • Tune rules from decisions.
  • Audit five hard rejects and five just below threshold each week.
  • Record each missed paper and the hiding rule.
  • Add an LLM reranker only after repeated static-ranking errors.
False-negative audit: once per week, sample five hard-rejected papers plus the five candidates immediately below the threshold. Record relevant misses and the exact rule that hid each paper.

Week-four decision gate

Keep BTune configuration when the digest saves time and static ranking is adequate.
Reduce to ARemove local automation when it saves too little time.
Adopt COperate learned ranking and a browser UI only when their value covers the extra work.

Pilot measures and weekly human loop

Measures

  • Precision at threeSurfaced papers marked keep or defer.
  • Deep-read conversionSurfaced papers that become full reading notes.
  • Miss rate auditRelevant papers in rejected or below-threshold samples.
  • Duplicate rateResurfaced papers that should have stayed suppressed.
  • Source yieldSelected papers attributed to each source.
  • Weekly triage timeDecision time excluding deep reading.
  • Empty-digest rateTrack it, but do not treat it as failure by itself.

Failure semantics

  • Prevent overlap. Run under a lock so timer overlap cannot create duplicate digests.
  • Bound retries. Retry each source independently with backoff.
  • Preserve freshness state. Keep the last successful response and timestamp per source.
  • Degrade by source. Continue when one source fails and mark stale or missing provenance.
  • Generate idempotently. Derive the digest from run date and candidate IDs.
  • Log enough to inspect. Record source counts, filter counts, selected IDs, errors, and runtime.
  • Limit alerts. Alert after two consecutive failed runs or when a source exceeds its expected stale interval.
  • Protect credentials. Keep API keys outside the repository and prefer adequate unauthenticated endpoints.

Non-goals

  • PDF download, parsing, OCR, or full-text embeddings
  • A vector database
  • A hosted multi-user service
  • Scraping alphaXiv, conference sites, or ResearchRabbit
  • Browser automation against Zotero or ResearchRabbit
  • Automatic project conclusions from abstracts
  • Hard-coded yearly conference calendars
  • Daily LLM processing of the full candidate pool
