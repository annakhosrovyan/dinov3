What actually compiles in Phase 7?

In the DDP champion path, run_ddp.sh does not select a special compile_mode. It sets train.cudagraphs=true, so every ViT backbone block enters the explicit fullgraph plus CUDA-graph branch. Heads are compiled separately with plain module.compile().

The important correction: DDP wrapping is not an alternate compile path. This repo compiles modules first, then wraps the student submodules in DDP.

Evidence: run_ddp.sh:111-138, config.py:71-90, ac_compile_parallelize.py:164-242.

Independent Review Verdict

Correct Branch 1 shadows compile_mode for backbone blocks when cudagraphs=true.

Needs precision A compile_mode override would affect heads across the compiled model dictionaries, not the backbone.

Stale The old "iBOT K varies every iteration" explanation is contradicted by current collate and mask-generator code at fixed per-GPU batch size.

What "fullgraph" Means Here

In this repo, fullgraph=True is only used on backbone blocks in the explicit branch-1 call. It requires the called block to be captured as one graph. It is not the same thing as mode="max-autotune".

What "CUDA graphs" Means Here

options={"triton.cudagraphs": True} asks Inductor to replay captured CUDA work to reduce CPU launch overhead. The Phase 6 fix cudagraph_mark_step_begin() is already in forward_backward().

What "max-autotune" Means Here

max_autotune profiles candidate matmul implementations and picks a faster one for supported shapes. It is about kernel choice, not launch replay. PyTorch exposes it through modes and through backend options.

Why The Jargon Gets Confusing

mode="max-autotune" bundles autotuning with CUDA graphs on GPU, but this repo currently bypasses the mode string for backbone blocks when cudagraphs=true. That is why a config flag cannot combine autotune with the champion branch today.

The iBOT Shape Story: What Changed

Old Phase 6 Helper

The old helper said mask_indices_list has a variable shape because mask counts are random. That matched the old comment in collate.py:63, but the implementation does not support it at fixed batch size.

Current Code

collate_data_and_cast() deterministically chooses how many samples are masked and how many patches each target should contain. complete_mask_randomly() tops every mask up to exactly its target count.

Current Caveat

Positions are still random, and changing per-GPU batch size changes the static K. Disabled paths such as multidistillation or some Gram token selections can have different shape behavior.

Phase 7 Decision Implications

Question Answer from current code Actionable implication
Does run_ddp.sh use max-autotune-no-cudagraphs? No. It leaves train.compile_mode at null. The champion baseline is backbone fullgraph plus CUDA graphs, not autotune.
Can a config-only override combine max-autotune with the champion backbone branch? No. With cudagraphs=true, branch 1 takes the backbone first. Combining them needs a code edit in wrap_compile_block().
Is max-autotune-no-cudagraphs useless? Not proven. It is a valid isolation test when cudagraphs=false. Use it only as an autotune go/no-go run, not as the final target.
Should Phase 7 spend engineering time making heads static? Not based on the current K evidence. The count is already static for the default fixed-bs path. Prioritize nsys attribution and a controlled autotune ladder.
