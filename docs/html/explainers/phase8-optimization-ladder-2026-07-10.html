Phase 8 — the optimization ladder

Phase 8 is a two-stage program: first remove host/storage arrival skew (the 7.9 straggler root cause), then optimize actual DDP communication. Comms-side levers — bucket caps, CUDA_DEVICE_MAX_CONNECTIONS, NVLS — are uninterpretable until rank-arrival skew is cleaned, because a single late rank makes every collective look slow. This page exists to make the sequencing of the nine candidate levers legible at a glance, not just their individual gain estimates.

torch-compile-dispatch-phase7

What actually compiles, and where.

The framing (accepted)

Comms-side experiments (buckets, CUDA_DEVICE_MAX_CONNECTIONS, NVLS) are uninterpretable until rank-arrival skew is cleaned — a late rank makes every collective look slow.

The "exposed NCCL ≈ 56% of p50 wall" figure is largely where late-rank waiting appears (NCCL LL kernels spin-wait), not 56% transferable communication. It is a symptom location, not a comms-optimization budget. That is why #1 (IRQ steering) has to run — or at least be probed — before the comms-tuning cluster (#3 screen, #5, #6) can produce a trustworthy read.

How the optimizations stack

This is the centerpiece: not which lever gives what gain in isolation, but which levers depend on which. #1 (root IRQ steering) is a gate — it sits outside the DDP/comms system entirely and unlocks a cluster of comms experiments that are meaningless without it. A separate cluster can run today, rootless, in parallel, because it never touches comms or the IRQ zone. A third cluster stays exploratory/deferred until a cheap probe clears a bar.

Gains are NOT additive. Many of these levers attack the same 56% comms wall or the same arrival-skew symptom (a late rank shows up as slow allreduce, slow bucket flush, slow NVLS path — one root cause, many observed locations). Summing the gain ranges in the table below (e.g. "8–20% + 0–8% + 0–5% + 0–5%") overcounts what is actually available. Treat the ranges as overlapping claims on the same underlying skew/comms budget, not independent, stackable wins.

Gate · shared infra · awaiting go

#1 Root IRQ steering

Needs root, an audit doc, and a reversal plan (same pattern as the earlier perf-sysctl change) before it touches shared infra across gpu01–08. This is the one item on the ladder that is a user decision, not an engineering task — everything in the gated amber cluster stays blocked until it is approved and run.

Killed levers (frozen-convergence constraint)

Verified in code — these are closed, not open questions.

  • bf16 gradient-compression DDP hooks: dead. The DDP path casts params to bf16 before wrapping (ac_compile_parallelize.py:336-343), so gradients already reduce in bf16; a hook saves zero bytes.
  • fp32-reduce tuning: reduce_dtype is FSDP2-policy-only (ac_compile_parallelize.py:269); the DDP path never uses it. Implementing fp32 DDP reduction would double traffic.
  • PowerSGD: approximate gradients + error-feedback state; conflicts with the convergence-parity requirement.

Corrections to our own framing (verified, adopt going forward)

  1. train.cudagraphs=true is per-block CUDA-graph capture, not full-step. wrap_compile_block() does module.compile(fullgraph=True, dynamic=False, options={"triton.cudagraphs": True}) per transformer block (ac_compile_parallelize.py:71). Do not claim "all gradients appear at replay end".
  2. 56% exposed NCCL ≠ 56% comms opportunity — it is where straggler wait shows up (spin-wait in LL kernels; lands in whichever collective the late rank hits).
  3. Logged mfu in training_metrics.json is CUDA-event-based (step_start_event→step_end_event). "Wall MFU" is a separate offline recomputation.
  4. 7.9 diagnosed the straggler; it is not remediated until IRQ steering runs. The bs192 w16 −17% is cross-node; only the bs160 −11%/−6% is node-controlled.

Decision log

2026-07-10 — in_order=False REJECTED (Aram). Data ordering for transformer pre-training is part of the training recipe, not a free knob: reproducibility and the data order/mix matter for convergence (the same reason pre-/mid-/post-training curricula exist). Out-of-order batch consumption would also break the sampler_advance = iterations × batch resume contract. Throughput is not worth either cost. Standing rule: no optimization that changes which samples arrive in which order.
2026-07-10 — rest of the ladder accepted as reasonable by Aram. IRQ steering (#1) still awaiting explicit go.

Short version

The queue-ready next steps are the three rootless screens — #7 fused AdamW, #3 bucket-logging dump, #2 worker hygiene — none of which touch comms or need root. #1 root IRQ steering is the force-multiplier gate: it is awaiting explicit user go, and until it runs, the comms-tuning cluster (#5 MAX_CONNECTIONS, #3 bucket-cap screen, #6 NVLS) stays uninterpretable because a late rank makes every collective look slow. Gains across the ladder do not simply add — most levers attack the same 56% comms/arrival-skew symptom, so treat the ranges as overlapping claims, not a stackable total.
