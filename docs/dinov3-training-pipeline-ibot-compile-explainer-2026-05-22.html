What Is iBOT?

iBOT is the masked-patch part of the self-supervised objective. DINO teaches the student to match the teacher on image-level global tokens. iBOT adds a patch-level task: hide some patch tokens from the student and ask the student to match teacher targets for those hidden locations.

iBOT applies masks only to global crops. Code anchors: dinov3/loss/ibot_patch_loss.py:61 defines iBOTPatchLoss; dinov3/train/ssl_meta_arch.py:585 gathers masked patch tokens and feeds student.ibot_head.

The Fixed Mask vs Variable Tokens Confusion

The short version, using repo names

collated_masks can have a fixed rectangular shape. The variable shape appears after collated_masks.flatten().nonzero().flatten() creates mask_indices_list. The length of mask_indices_list is the number of true mask entries in that batch, and the iBOT path gathers exactly that many patch tokens. 

# Actual code: dinov3/data/collate.py:63
mask_indices_list = collated_masks.flatten().nonzero().flatten()

# Actual code: dinov3/data/collate.py:74
"n_masked_patches": torch.full(
    (1,),
    fill_value=mask_indices_list.shape[0],
    dtype=torch.long,
)

# Actual code: dinov3/train/ssl_meta_arch.py:585
masked_patches_pre_head = torch.index_select(
    g_patch.flatten(0, 1),
    dim=0,
    index=mask_indices_list,
)

Any simplified phrase like tokens[mask] is only a translation of the actual repo flow above: collated_masks becomes mask_indices_list, then mask_indices_list is used as the index argument to torch.index_select.

Where This Happens in Code

The dataloader/collate path creates a rectangular mask and then turns all true positions into a compact one-dimensional list of indices: 

# dinov3/data/collate.py:63
mask_indices_list = collated_masks.flatten().nonzero().flatten()

# dinov3/data/collate.py:74
"n_masked_patches": torch.full((1,), fill_value=mask_indices_list.shape[0], dtype=torch.long)

Later, the training step uses that list to gather only the masked patch tokens: 

# dinov3/train/ssl_meta_arch.py:585
masked_patches_pre_head = torch.index_select(g_patch.flatten(0, 1), dim=0, index=mask_indices_list)

The iBOT loss also carries this variable count forward: 

# dinov3/loss/ibot_patch_loss.py:115
loss = loss[:n_masked_patches]

One-sentence answer to give back

The input and collated_masks shapes can be fixed, but our iBOT path materializes only the selected masked tokens through mask_indices_list; that selected-token tensor has first dimension mask_indices_list.shape[0], and that value can vary.

What About masks_weight?

masks_weight is related, but it is not the main line when talking about the dynamic iBOT selected-token shape. The main shape-changing path is mask_indices_list into torch.index_select. 

# dinov3/data/collate.py:65
masks_weight = (
    1 / collated_masks.sum(-1).clamp(min=1.0)
).unsqueeze(-1).expand_as(collated_masks)[collated_masks]

This line also uses boolean selection at the end: [collated_masks]. That means masks_weight also has one entry per true mask value, so it is part of the same variable-count story. But the token tensor sent through student.ibot_head is selected by mask_indices_list.

Why torch.compile Cares

torch.compile tries to turn Python/PyTorch execution into optimized graphs. It is happiest when the same operations see the same tensor shapes every iteration. In this code path, the first dimension of masked_patches_pre_head follows mask_indices_list.shape[0] = K. If K changes, the compiler must recompile or introduce a dynamic-shape guard.

Default compile (this repo)

train.compile=true and train.cudagraphs=false compiles selected transformer blocks in default mode. This tolerates dynamic shapes by falling back to eager execution for affected operations — no hard recompile storm, but also no CUDA graph replay.

fullgraph + CUDA graphs

When train.cudagraphs=true, the repo calls module.compile(fullgraph=True, dynamic=False, options={"triton.cudagraphs": True}). Variable K breaks this path because dynamic=False and static CUDA graph replay both assume shape stability.

Compile anchors: dinov3/fsdp/ac_compile_parallelize.py:65-76 defines wrap_compile_block() — the branch point between default compile and fullgraph+cudagraphs; ac_compile_parallelize.py:97-101 applies it per ViT block.

What Phase 6 Is Testing

6.1 Diagnose current compile

Re-run the DDP compile recipe with Dynamo logs for recompiles, graph breaks, and dynamic-shape guards.

6.2 Backbone-only CUDA graphs

Flip the repo's CUDA graph branch for backbone blocks and see whether the model core benefits.

6.3 Static iBOT pilot

Pad or bucket the selected masked-token path so masked_patches_pre_head has a fixed first dimension, then ignore padded entries in the loss.

6.4 Combine

Try DDP plus fullgraph/CUDA graphs plus static iBOT shapes and judge steady-state MFU/step time.

The trade-off

Padding makes shapes compiler-friendly, but it may compute on padded dummy tokens. The question is whether the saved launch/compile overhead is worth the extra padded-token work.
