DINOv3 Training Pipeline, iBOT, and Compile/CUDA Graphs

A beginner-friendly map of the training loop, model pieces, iBOT masked-patch objective, and why dynamic masking matters for torch.compile and CUDA graphs.

How To Learn This

Do not start with CUDA graphs. Start with the training objective. Once the pipeline is clear, the compiler problem becomes much less mysterious.

  1. Understand the data flow: crops and masks go into a student/teacher self-supervised model.
  2. Understand the losses: DINO CLS loss, iBOT masked patch loss, and KoLeo regularization.
  3. Find the dynamic shape: not image height/width, but the number of selected masked patch tokens.
  4. Connect that dynamic shape to PyTorch compile, graph breaks, recompiles, and CUDA graph replay.

One-Sentence Mental Model

DINOv3 self-supervised training creates multiple views of each image, runs a student and teacher network, asks the student to match the teacher at both image-level and masked-patch-level, then updates only the student while the teacher follows as an EMA copy.

Why this matters for performance The training step is not just "run a ViT once." It is multi-crop, student-teacher, multi-loss, distributed, and partially stochastic. That is why compiler assumptions about repeated identical shapes can break.

The Training Pipeline

1. Dataset sampleRaw image-like data is augmented into multiple crops.
2. CollateBatch builder stacks crops and creates patch masks.
3. TeacherTeacher sees global crops and produces targets.
4. StudentStudent sees global + local crops and predicts.
5. Loss + updateDINO, iBOT, KoLeo losses drive student update; teacher follows by EMA.

What Is iBOT?

iBOT is a masked image modeling objective used alongside DINO. It is not specific to this fork. In this repo it is implemented as a first-class DINOv3 loss.

DINO Loss

Works mostly at the image-summary level. The teacher and student produce CLS-token outputs. The student is trained to match teacher targets across crops.

Code: ssl_meta_arch.py:85,488,642-664.

iBOT Loss

Works at the patch level. Some patches are masked/selected; the student predicts teacher-style patch targets for those selected patches.

Code: ibot_patch_loss.py:61, ssl_meta_arch.py:129,672-680.

Plain-English analogy DINO asks: "Do these different views of the same image produce compatible overall representations?" iBOT asks: "Can the model infer useful patch-level information when only some patch positions are supervised?"

The Dynamic Masking Problem

The shape issue is not simply whether images are resized to fixed dimensions. The key dynamic shape is the number of masked patch tokens.

mask_indices_list = collated_masks.flatten().nonzero().flatten()

That line means: flatten the mask, find every location that is masked, and return the indices of those locations. If this batch masks 7,503 patches, the tensor has length 7,503. If the next batch masks 7,489 patches, the tensor has length 7,489.

Code: dinov3/data/collate.py:63,100,107.

Answer to Armen's fixed-shape question Yes, the crops can be fixed-size. But iBOT creates a second downstream shape: "how many masked patches were selected this batch?" That count is stochastic, and that is the shape that can break static compile/CUDA graph assumptions.

global_crops, local_cropsUsually fixed per crop type.Backbone-only CUDA graphs may be feasible.

What Is torch.compile?

torch.compile asks PyTorch to observe Python/PyTorch execution, capture regions as graphs, and lower those graphs into optimized execution. In this repo we usually reach it through nn.Module.compile().

if use_cuda_graphs and is_backbone_block:
    module.compile(fullgraph=True, dynamic=False, options={"triton.cudagraphs": True})
elif compile_mode is not None:
    module.compile(mode=compile_mode)
else:
    module.compile()

Code: ac_compile_parallelize.py:65-76.

Key distinction "Compile is on" does not mean "we are using the strictest, fastest, static-shape path." Phase 5 mostly used plain module.compile(). Armen is asking about the stricter fullgraph=True / CUDA graph path.

What Are CUDA Graphs?

CUDA graphs are a GPU launch optimization. Instead of the CPU launching many kernels one by one every iteration, a repeated launch sequence can be captured once and replayed more cheaply.

Why they can help

  • Large training steps launch many GPU kernels.
  • CPU launch overhead and Python overhead can become visible.
  • Replay is cheaper if the same sequence repeats with the same shapes and memory patterns.

Why they are strict

  • Shapes should be stable.
  • Control flow should be stable.
  • Memory addresses and allocation patterns are harder to vary.
  • Unsupported Python/PyTorch operations can cause capture failure.

That is why iBOT dynamic masking is not a cosmetic issue. It changes the shape of tensors in the training step.

What You Should Be Able To Explain After Reading This

  • iBOT is a masked patch prediction objective, not a fork-only feature.
  • The model has fixed crop sizes, but iBOT can still create variable-length masked-token tensors.
  • train.compile=true means this repo enables PyTorch compile wrappers, not necessarily fullgraph CUDA graphs.
  • fullgraph=True is both an optimization attempt and a diagnostic: if it fails, the failure tells us what blocks graph capture.
  • Phase 6 should test the easy static part first, then make the dynamic iBOT path static via padding/bucketing, then run the end-to-end fullgraph/CUDA graph experiment.
